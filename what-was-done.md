## 2. Предварительно зафиксировать контракты и правила

Файл `README.md` полностью наполнен описанием будущих API-контрактов и бизнес-правил. Это сделано до написания бизнес-логики, чтобы оба микросервиса использовали одинаковые форматы данных и одинаково понимали процесс бронирования.

### 2.1. Зафиксированы компоненты и порты

| Компонент | Имя в Eureka | Порт |
|---|---|---:|
| API Gateway | `api-gateway` | 8080 |
| Hotel Management Service | `hotel-service` | 8081 |
| Booking Service | `booking-service` | 8082 |
| Eureka Server | — | 8761 |

Определено, что внешние клиенты обращаются через Gateway. Межсервисные вызовы выполняются по логическому имени сервиса через Eureka, а не через жёстко записанные IP-адреса.

Внутренние операции `confirm-availability` и `release` не должны публиковаться через Gateway.

### 2.2. Зафиксированы общие форматы данных

В README определено:

- JSON является форматом запросов и ответов;
- даты передаются как `yyyy-MM-dd`;
- `requestId` имеет формат UUID;
- защищённые запросы используют заголовок `Authorization: Bearer <JWT>`;
- пользовательский JWT действует один час;
- ошибки возвращаются в формате `application/problem+json` через Spring `ProblemDetail`.

Пример зафиксированного ответа с ошибкой:

```json
{
  "type": "about:blank",
  "title": "Conflict",
  "status": 409,
  "detail": "Room is not available for the requested dates",
  "instance": "/booking",
  "requestId": "6a18c94f-f26b-4f3d-994d-665c49d8b51e"
}
```

### 2.3. Описаны эндпойнты Booking Service

Зафиксированы публичные операции:

- `POST /user/register` — регистрация и получение JWT;
- `POST /user/auth` — вход и получение JWT;
- `POST /booking` — создание брони;
- `GET /bookings` — история текущего пользователя;
- `GET /booking/{id}` — получение своей брони;
- `DELETE /booking/{id}` — отмена своей брони.

Зафиксированы административные операции:

- `POST /user`;
- `PATCH /user`;
- `DELETE /user?id={id}`.

Для них определены роли, HTTP-коды успешных ответов и DTO. Например, запрос на создание брони имеет следующий вид:

```json
{
  "requestId": "6a18c94f-f26b-4f3d-994d-665c49d8b51e",
  "roomId": 10,
  "startDate": "2026-11-10",
  "endDate": "2026-11-15",
  "autoSelect": false
}
```

Установлено, что при `autoSelect=true` значение `roomId` игнорируется, а при `autoSelect=false` поле `roomId` обязательно.

Для идемпотентности определено:

- повтор с тем же `requestId` и теми же параметрами возвращает существующую бронь;
- повтор с тем же `requestId`, но другими параметрами отклоняется с кодом 409;
- повторная отмена уже отменённой брони не создаёт ошибку и возвращает 204.

### 2.4. Описаны эндпойнты Hotel Service

Зафиксированы операции с отелями:

- `POST /api/hotels`;
- `GET /api/hotels`;
- `PATCH /api/hotels/{id}`;
- `DELETE /api/hotels/{id}`.

Зафиксированы операции с номерами:

- `POST /api/rooms`;
- `GET /api/rooms`;
- `GET /api/rooms/recommend`;
- `PATCH /api/rooms/{id}`;
- `DELETE /api/rooms/{id}`.

Для получения свободных и рекомендованных номеров определены обязательные параметры:

```text
GET /api/rooms?startDate=2026-11-10&endDate=2026-11-15
GET /api/rooms/recommend?startDate=2026-11-10&endDate=2026-11-15
```

Также описаны внутренние вызовы:

- `POST /api/rooms/{id}/confirm-availability`;
- `POST /api/rooms/{id}/release`.

Для них предусмотрен отдельный служебный JWT с ролью INTERNAL.

### 2.5. Определены правила доступности номеров

Зафиксированы следующие правила:

- `startDate` должна быть раньше `endDate`;
- бронирование использует интервал `[startDate, endDate)`;
- дата выезда одного гостя может быть датой заезда следующего;
- пересечение дат определяется условием:

```text
startDate < existingEndDate && endDate > existingStartDate
```

- `available=false` означает вывод номера из эксплуатации;
- `available=true` не гарантирует свободность на конкретные даты;
- занятость определяется по активным записям о бронированиях/слотах;
- рекомендации сортируются по `timesBooked ASC, id ASC`.

Отдельно определено поведение `timesBooked`: счётчик увеличивается один раз при успешном подтверждении, компенсация неудачного создания отменяет это увеличение, а обычная отмена подтверждённой брони сохраняет историческую статистику.

### 2.6. Описан распределённый сценарий бронирования

В README зафиксирована последовательность без глобальной распределённой транзакции:

1. Booking Service проверяет запрос и `requestId`.
2. В отдельной локальной транзакции создаётся бронь `PENDING`.
3. Booking Service вызывает `confirm-availability` в Hotel Service.
4. Hotel Service атомарно проверяет доступность и создаёт слот.
5. После успеха Booking Service переводит бронь в `CONFIRMED`.
6. При ошибке или тайм-ауте Booking Service вызывает `release` и переводит бронь в `CANCELLED`.
7. После тайм-аута `release` вызывается даже при неизвестном результате confirm, поскольку удалённая блокировка могла уже появиться.

Это необходимо, чтобы ошибка между двумя независимыми базами не оставляла активную бронь или блокировку в противоречивом состоянии.

### 2.7. Зафиксированы правила безопасности и ошибок

Определены роли:

- USER — личные бронирования и просмотр отелей/номеров;
- ADMIN — управление пользователями, отелями и номерами;
- INTERNAL — только внутренние confirm/release.

Каждый backend-сервис должен самостоятельно проверять JWT. Gateway не заменяет эту проверку.

Также определено использование кодов 400, 401, 403, 404, 409 и 503, правила тайм-аутов, ограниченных повторов и конкурентной блокировки номера.

## 4. Этап 2 — настроить Eureka и маршрутизацию Gateway

Этап реализован и проверен на реально запущенных приложениях.

### 4.1. Настроена регистрация сервисов в Eureka

В `hotel-service/src/main/resources/application.yml` и `booking-service/src/main/resources/application.yml` явно включены регистрация и получение реестра:

```yaml
eureka:
  client:
    register-with-eureka: true
    fetch-registry: true
    service-url:
      defaultZone: http://localhost:8761/eureka/
```

`register-with-eureka` позволяет сервису зарегистрировать свой адрес в Eureka, а `fetch-registry` — получать сведения о других сервисах.

Приложения регистрируются под именами `hotel-service` и `booking-service`. Благодаря этому Gateway обращается к ним по логическому имени, а не по захардкоженному IP-адресу.

### 4.2. Добавлены маршруты API Gateway

В `api-gateway/src/main/resources/application.yml` созданы два маршрута:

```yaml
spring:
  cloud:
    gateway:
      server:
        webflux:
          routes:
            - id: hotel-service-public
              uri: lb://hotel-service
              predicates:
                - Path=/api/hotels,/api/hotels/{hotelId},/api/rooms,/api/rooms/recommend,/api/rooms/{roomId}
            - id: booking-service-public
              uri: lb://booking-service
              predicates:
                - Path=/user,/user/register,/user/auth,/booking,/booking/{bookingId},/bookings
```

Префикс `lb://` означает, что Gateway выбирает экземпляр сервиса через Service Discovery и балансировщик нагрузки.

Маршрут Hotel Service охватывает:

- список и CRUD отелей;
- создание, обновление и удаление номеров;
- получение свободных номеров;
- получение рекомендаций.

Маршрут Booking Service охватывает:

- регистрацию и аутентификацию;
- администрирование пользователей;
- создание, просмотр и отмену бронирований;
- историю бронирований.

Автоматическая маршрутизация через Eureka Discovery Locator отключена. Поэтому в Gateway попадают только явно перечисленные пути, а новый backend-эндпойнт не становится публичным автоматически.

### 4.3. Сохранены пути и исключены внутренние операции

Не используются `StripPrefix`, `RewritePath` или другие фильтры изменения URL. Путь запроса передаётся backend-сервису без изменений. Заголовки запроса, включая `Authorization`, также передаются downstream-сервису.

Шаблон `/api/rooms/{roomId}` принимает только один сегмент после `/rooms`. Поэтому следующие внутренние пути не совпадают с публичным маршрутом:

```text
/api/rooms/{id}/confirm-availability
/api/rooms/{id}/release
```

Они не опубликованы через Gateway. Их JWT-защита с ролью INTERNAL будет добавлена на этапе настройки безопасности.

Полная сборка проекта выполнена командой:

```

Результат — `BUILD SUCCESS` для всех модулей.

### 5.1. Создана JPA-модель Hotel Service

В пакете `hotel-service/src/main/java/skillfactory/luzhin/hotel/entity` созданы следующие классы:

- `Hotel` — сущность отеля с полями `id`, `name`, `address` и связью `@OneToMany` с номерами;
- `Room` — сущность номера с полями `id`, `hotel`, `number`, `available` и `timesBooked`;
- `RoomReservation` — отдельная запись о занятости номера с полями `bookingId`, `requestId`, `room`, `startDate`, `endDate`, `status` и `createdAt`;
- `RoomReservationStatus` — состояния записи занятости `HELD` и `RELEASED`.

Связь номера с отелем реализована через `@ManyToOne` и внешний ключ `hotel_id`. Для таблицы `rooms` добавлено составное уникальное ограничение по `hotel_id` и `number`, поэтому одинаковый номер комнаты не может быть создан дважды в одном отеле, но допускается в разных отелях.

Для `room_reservations` добавлены уникальные ограничения по `booking_id` и `request_id`. Они закладывают основу идемпотентной обработки будущих confirm/release. Записи занятости хранятся в базе Hotel Service, а не в базе Booking Service. Для идентификатора запроса используется `UUID`, для дат — `LocalDate`, для времени создания — `Instant`.

Поле `Room.available` остаётся признаком эксплуатационной доступности. Оно не используется как признак занятости на конкретные даты.

### 5.2. Добавлены репозитории

В пакете `repository` созданы:

- `HotelRepository` — стандартные операции Spring Data JPA с отелями;
- `RoomRepository` — операции с номерами, проверка уникальности номера комнаты в отеле и JPQL-запрос свободных номеров;
- `RoomReservationRepository` — проверки наличия активной или исторической занятости номера и любого номера отеля.

Запрос доступности выбирает только номера с `available=true` и исключает номера, для которых существует активный слот `HELD` с пересекающимися датами. Пересечение проверяется согласно контракту:

```text
startDate < existingEndDate && endDate > existingStartDate
```

Таким образом используется интервал `[startDate, endDate)`, а дата выезда одного гостя может совпадать с датой заезда следующего. Освобождённые записи `RELEASED` не участвуют в исключении номера из результата.

Метод запроса принимает `Sort`. Обычный список свободных номеров запрашивается без специальной сортировки, а для рекомендаций передаётся сортировка `timesBooked ASC, id ASC`.

### 5.3. Добавлены DTO и MapStruct-мапперы

В пакете `dto` созданы отдельные модели запросов и ответов:

- `HotelCreateRequest` и `HotelUpdateRequest`;
- `HotelResponse`;
- `RoomCreateRequest` и `RoomUpdateRequest`;
- `RoomResponse`.

Для создания используются ограничения Bean Validation: обязательные название и адрес отеля, обязательные `hotelId` и `number` номера, положительный `hotelId`, ограничения длины строк и запрет пустых значений. В PATCH-запросах поля необязательны, но переданные значения проверяются. Поле `available` при создании необязательно.

В пакете `mapper` созданы `HotelMapper` и `RoomMapper` с `componentModel="spring"`. Мапперы преобразуют сущности в DTO ответов, создают сущности из запросов и выполняют частичное обновление через `@MappingTarget`. При PATCH значения `null` игнорируются, поэтому непереданные поля сохраняют прежние значения. При создании номера отсутствующее `available` преобразуется в `true`, а начальное значение `timesBooked` остаётся равным нулю.

Контроллеры получают и возвращают только DTO; JPA-сущности наружу не передаются.

### 5.4. Реализован сервисный слой и бизнес-правила

В пакете `service` созданы `HotelService` и `RoomService`. Классы используют `@Transactional(readOnly = true)` для операций чтения и отдельные `@Transactional` для создания, обновления и удаления.

`HotelService` реализует:

- создание отеля;
- получение списка отелей;
- частичное обновление отеля;
- удаление отеля.

`RoomService` реализует:

- создание номера только в существующем отеле;
- получение свободных номеров на даты;
- получение рекомендаций;
- частичное обновление номера, включая изменение отеля, номера комнаты и эксплуатационной доступности;
- удаление номера.

Дополнительно реализованы правила:

- `startDate` должна быть строго раньше `endDate`;
- отсутствующие отель или номер приводят к ошибке 404;
- дубликат номера комнаты в одном отеле приводит к ошибке 409;
- уникальность дополнительно обеспечивается ограничением БД, а не только предварительной проверкой;
- удаление номера с активной или исторической записью занятости запрещено с ошибкой 409;
- удаление отеля с записью занятости хотя бы одного номера запрещено с ошибкой 409;
- отель без истории занятости удаляется вместе со своими номерами через каскадное удаление JPA;
- рекомендации сортируются строго по `timesBooked ASC, id ASC`.

### 5.5. Реализованы REST-контроллеры

В пакете `controller` созданы `HotelController` и `RoomController`. Реализованы следующие публичные операции из зафиксированного README-контракта:

### 5.6. Добавлена обработка ошибок

В пакете `exception` созданы:

- `ResourceNotFoundException` для отсутствующих ресурсов;

## 6. Этап 4 — реализовать пользователей и аутентификацию в Booking Service

Автоматические тесты из подпункта 6.6 пока не добавлялись. Самостоятельная проверка JWT backend-сервисами и разграничение доступа по ролям относятся к следующему этапу плана и пока не настроены.

### 6.1. Подключены библиотеки безопасности

В `booking-service/pom.xml` добавлены управляемые Spring Boot зависимости:

Версии явно не дублируются в дочернем POM. На данном этапе не подключалась автоматическая цепочка Spring Security Filter и не настраивался Resource Server: это работа этапа 5 плана.

### 6.2. Создана модель пользователей

В пакете `booking-service/src/main/java/skillfactory/luzhin/booking/entity` созданы:

- `User` — JPA-сущность с полями `id`, `username`, `password` и `role`;
- `UserRole` — роли `USER` и `ADMIN`.

Таблица `users` находится только в H2 Booking Service. Для `username` добавлено уникальное ограничение БД `uk_users_username`. Роль сохраняется как строка через `@Enumerated(EnumType.STRING)`. Пароль хранится только в поле с BCrypt-хешем длиной до 60 символов.

В пакете `repository` создан `UserRepository` с операциями `findByUsername` и `existsByUsername`. Они используются для входа и предварительной проверки дубликатов; уникальность дополнительно гарантируется ограничением БД.

### 6.3. Добавлены DTO и маппер

Созданы следующие DTO:

- `CredentialsRequest` — общий запрос регистрации и входа с `username` и `password`;
- `UserCreateRequest` — административное создание пользователя с явной ролью;
- `UserUpdateRequest` — частичное обновление с обязательным положительным `id` и необязательными остальными полями;
- `UserResponse` — безопасный ответ с `id`, `username` и `role`;
- `AuthResponse` — ответ с `accessToken`, `tokenType` и `expiresIn`.

Добавлена Bean Validation: обязательные учётные данные, минимальная длина пароля 8 символов, ограничения длины, обязательная роль при административном создании и запрет пустого переданного username при PATCH.

`UserMapper` на MapStruct преобразует `User` в `UserResponse`. Наружу возвращаются только DTO: пароль, BCrypt-хеш и внутренняя JPA-сущность в ответы не попадают.

### 6.4. Реализованы регистрация и вход

`AuthService` реализует два сценария:

- регистрация всегда создаёт пользователя с ролью `USER`, независимо от данных клиента;
- вход находит пользователя по username и проверяет пароль через `PasswordEncoder.matches`.

Перед сохранением пароль преобразуется через `BCryptPasswordEncoder`. При повторной регистрации существующего username возвращается конфликт 409. При неверном username или пароле возвращается одинаковая ошибка `Invalid username or password` с кодом 401, без раскрытия того, какая именно часть учётных данных неверна.

После успешной регистрации или входа пользователь получает JWT. Регистрация выполняется в локальной транзакции, чтение пользователя при входе — в read-only транзакции.

### 6.5. Реализован выпуск JWT на один час

В пакете `config` созданы:

- `JwtProperties` для секрета и issuer;
- `BookingSecurityConfig` с beans `PasswordEncoder`, `JwtEncoder` и `Clock`;
- `JwtService` для формирования и подписи токена.

Используется симметричный алгоритм HS256. Секрет считывается из конфигурации и проверяется при запуске: для ключа требуется минимум 32 байта. JWT содержит:

- `sub` — строковый идентификатор пользователя;
- `username` — имя пользователя;
- `role` — роль `USER` или `ADMIN`;
- `iss` — издатель токена;
- `iat` — время выпуска;
- `exp` — время истечения.

Срок действия фиксирован константой 3600 секунд, поэтому `exp - iat` всегда равно одному часу. Ответ имеет `tokenType=Bearer` и `expiresIn=3600`. Источник времени вынесен в `Clock`, что позволит детерминированно тестировать claims на следующем шаге.

В `application.yml` добавлены внешние настройки:

```text
JWT_SECRET
JWT_ISSUER
```

Для локального запуска предусмотрен отдельный явно локальный секрет по умолчанию; реальные секреты должны передаваться через переменную окружения и не коммититься.

### 6.6. Реализовано администрирование пользователей

`UserService` реализует:

- создание пользователя с ролью `USER` или `ADMIN`;
- частичное обновление username, пароля и роли;
- удаление пользователя по идентификатору.

При смене пароля он заново хешируется через BCrypt. При смене username выполняется проверка уникальности. Отсутствующий пользователь приводит к 404, дубликат username — к 409. Операции используют локальные транзакции.

Ограничение удаления пользователя с историей бронирований будет подключено после появления сущности `Booking` на этапе 6 плана. На текущем этапе такой истории в базе ещё нет. Авторизация этих операций только для ADMIN будет добавлена на этапе настройки Spring Security.

```text

Если пользователь с указанным username уже существует, повторное создание не выполняется. Пароль начального ADMIN сохраняется только как BCrypt-хеш.

| Операции | Доступ |

## 8. Этап 6 — реализовать локальную модель бронирований

Реализованы локальная сущность бронирования, REST API, идемпотентное создание PENDING, история текущего пользователя, получение и отмена собственной записи. Проверка владения использует subject пользовательского JWT. Распределённый вызов Hotel Service намеренно ещё не выполняется: автоподбор фактического номера, переход в CONFIRMED и компенсация относятся к этапу 7.

### 8.1. Создана JPA-модель бронирований

В пакете `booking-service/src/main/java/skillfactory/luzhin/booking/entity` добавлены:

- `Booking` — сущность локальной брони;
- `BookingStatus` — статусы `PENDING`, `CONFIRMED` и `CANCELLED`.

`Booking` содержит:

- `id`;
- связь `@ManyToOne` с владельцем `User` через `user_id`;
- `roomId`;
- `startDate` и `endDate`;
- `status`;
- `requestId` в формате UUID;
- `autoSelect`;
- `createdAt` и `updatedAt`.

Для `requestId` добавлено уникальное ограничение БД `uk_bookings_request`. Оно не позволяет создать две записи для одного клиентского запроса и дополняет проверку идемпотентности в сервисном слое.

Поле `roomId` может быть пустым у PENDING-брони с `autoSelect=true`: фактический номер будет выбран через Hotel Service на следующем этапе. Для ручного выбора `roomId` обязателен. Владелец хранится связью с пользователем, поэтому история бронирований участвует в целостности данных при удалении пользователя.

### 8.2. Добавлены DTO, репозиторий и MapStruct-маппер

Созданы:

- `BookingCreateRequest` с `requestId`, `roomId`, `startDate`, `endDate` и `autoSelect`;
- `BookingResponse` с публичными полями `id`, `userId`, `roomId`, датами, статусом и `createdAt`;
- `BookingMapper`, который получает `userId` из связанного пользователя;
- `BookingCreationResult`, позволяющий различать новую запись и идемпотентный повтор.

Bean Validation проверяет обязательные `requestId`, даты и `autoSelect`, а также положительный переданный `roomId`. Идентификатор брони в пути проверяется на положительное значение. Наружу возвращается DTO без внутренних полей сущности.

`BookingRepository` предоставляет:

- поиск по `requestId`;
- историю по `userId` с сортировкой `createdAt DESC, id DESC`;
- поиск `id` только вместе с `userId` владельца;
- проверку наличия истории бронирований пользователя.

### 8.3. Реализовано идемпотентное создание PENDING-брони

`BookingService.create` выполняется в локальной транзакции и не содержит HTTP-вызовов внутри неё.

Перед созданием проверяются:

- существование пользователя из `sub` JWT;
- обязательность `roomId` при `autoSelect=false`;
- условие `startDate < endDate`;
- наличие записи с тем же `requestId`.

При ручном выборе сохраняется переданный `roomId`. При автоподборе значение `roomId` игнорируется, а в PENDING-записи остаётся `null` до обращения к Hotel Service.

Новая запись получает статус PENDING и одинаковые начальные `createdAt`/`updatedAt`, после чего контроллер возвращает 201.

Если `requestId` уже существует:

- при совпадении пользователя и бизнес-параметров возвращается исходная бронь с кодом 200;
- новая запись не создаётся;
- при `autoSelect=true` изменение переданного `roomId` не считается изменением бизнес-параметров;
- при другом пользователе, номере, датах или режиме выбора возвращается 409 без раскрытия чужой брони.

Таким образом реализованы последовательные идемпотентные повторы. Обработка параллельных одинаковых `requestId` с возвратом исходной записи после гонки будет усилена на этапе конкурентной безопасности.

### 8.4. Реализованы история, владение и отмена

Добавлен `BookingController` с операциями:

| Метод и путь | Текущий результат |
|---|---|
| `POST /booking` | PENDING-бронь, 201; идемпотентный повтор — 200 |
| `GET /bookings` | История только текущего пользователя, 200 |
| `GET /booking/{id}` | Получение собственной брони, 200 |
| `DELETE /booking/{id}` | Отмена собственной PENDING-брони, 204 |

Идентификатор пользователя извлекается из `sub` JWT. Некорректный или неположительный subject отклоняется с ошибкой 400.

Получение и отмена используют запрос `findByIdAndUserId`. Если запись принадлежит другому пользователю, API возвращает 404 так же, как для отсутствующей записи, и не раскрывает её содержимое.

Отмена PENDING переводит запись в CANCELLED и обновляет `updatedAt`. Повторная отмена CANCELLED ничего не изменяет и возвращает 204.

Локальная отмена CONFIRMED без удалённого release запрещена: сервис возвращает 503 и сохраняет статус CONFIRMED. Это предотвращает ложный успех и расхождение с занятостью номера в Hotel Service. ## 9. Этап 7 — реализовать двухшаговое подтверждение и компенсацию

Реализован полный распределённый сценарий создания и отмены бронирования. Booking Service выбирает номер, фиксирует PENDING в отдельной локальной транзакции, вызывает Hotel Service и переводит бронь в CONFIRMED только после успешного удалённого confirm. При ошибке выполняется release и компенсация PENDING в CANCELLED. Отмена CONFIRMED теперь также освобождает занятость через Hotel Service.

### 9.1. Добавлены внутренние DTO и REST-контроллер Hotel Service

В Hotel Service созданы модели внутренних запросов и ответов:

- `ConfirmAvailabilityRequest` — `bookingId`, `requestId`, `startDate` и `endDate`;
- `ReleaseReservationRequest` — `bookingId`, `requestId` и причина освобождения;
- `ReleaseReason` — значения `COMPENSATION` и `USER_CANCELLATION`;
- `RoomReservationResponse` — `bookingId`, `roomId` и состояние `HELD`/`RELEASED`.

Bean Validation проверяет обязательные поля, положительный `bookingId`, формат UUID и даты. Некорректный интервал по-прежнему отклоняется с кодом 400.

Создан `RoomReservationController` с операциями:

| Метод и путь | Результат |
|---|---|
| `POST /api/rooms/{id}/confirm-availability` | Создание или повторное получение блокировки, 200 |
| `POST /api/rooms/{id}/release` | Идемпотентное освобождение блокировки, 200 |

Контроллеры используют уже настроенные правила Spring Security: обе операции доступны только служебному JWT с ролью INTERNAL. Публичные маршруты Gateway не изменялись, поэтому внутренние операции остаются недоступными внешним клиентам.

### 9.2. Реализовано атомарное подтверждение доступности

Добавлен `RoomReservationService`, который выполняет confirm в одной локальной транзакции Hotel Service.

Для номера добавлен репозиторный запрос `findByIdForUpdate` с блокировкой `PESSIMISTIC_WRITE`. После получения блокировки строки номера сервис:

1. Проверяет эксплуатационную доступность `Room.available`.
2. Проверяет пересечение запрошенного интервала с активными записями `HELD`.
3. Создаёт запись `RoomReservation` со статусом `HELD`.
4. Увеличивает `timesBooked` ровно один раз.

Пересечение проверяется отдельным JPQL-запросом по правилу:

```text
startDate < existingEndDate && endDate > existingStartDate
```

При недоступности номера или пересечении дат возвращается 409 `Room is not available for the requested dates`, новая запись занятости не создаётся, а счётчик не изменяется.

В `RoomReservationRepository` добавлены поиск по `bookingId` и `requestId`. Повторный confirm той же операции возвращает существующий результат без второй записи и повторного увеличения счётчика. Изменённые идентификаторы, номер или даты при повторе приводят к 409. Повторный confirm после release возвращает состояние существующей записи и не воскрешает освобождённую блокировку.

### 9.3. Реализовано идемпотентное освобождение и правила статистики

Операция release находит исходную блокировку по `bookingId`/`requestId` и проверяет её соответствие номеру. При активном состоянии `HELD` запись переводится в `RELEASED`.

Правила изменения `timesBooked` соответствуют README:

- `COMPENSATION` отменяет увеличение счётчика, выполненное при confirm;
- `USER_CANCELLATION` сохраняет историческую статистику успешного бронирования;
- повторный release не изменяет запись и счётчик повторно;
- release после неуспешного confirm без установленной блокировки возвращает `RELEASED`, но не создаёт новую запись занятости.

Освобождённые записи не участвуют в последующих проверках доступности, поэтому номер снова может быть выбран на те же даты.

### 9.4. Добавлен HTTP-клиент Hotel Service через Service Discovery

В Booking Service созданы `HotelClientConfig` и `HotelServiceClient` на основе Spring `RestClient`.

Load-balanced builder объявлен через `@LoadBalanced`, а базовый адрес клиента — `http://hotel-service`. Поэтому конкретный хост и порт Hotel Service не зашиты в сценарий: экземпляр выбирается через Eureka и Spring Cloud LoadBalancer. Явное объявление builder также обеспечивает создание контекста в тестовом профиле с отключённым Service Discovery.

Клиент реализует три операции:

- получение `/api/rooms/recommend` для автоподбора;
- вызов `/api/rooms/{id}/confirm-availability`;
- вызов `/api/rooms/{id}/release`.

Для получения рекомендаций передаётся JWT текущего USER, поскольку это публичная пользовательская операция Hotel Service. Confirm и release подписываются отдельным служебным JWT с ролью INTERNAL через уже существующий `InternalJwtService`. Полные токены в ответы и журнал проверки не выводятся.

HTTP-ошибки Hotel Service преобразуются в ошибки Booking Service: 400 — некорректные параметры, 404 — отсутствующий номер, 409 — бизнес-конфликт, сетевые и остальные неуспешные ответы — 503. Настройка отдельных тайм-аутов и повторных попыток относится к следующему этапу и здесь не добавлялась.

### 9.5. Реализован оркестратор двухшагового подтверждения

Локальные транзакции вынесены в новый `BookingPersistenceService`. `BookingService` стал оркестратором распределённого сценария и сам не открывает транзакцию вокруг HTTP-вызовов.

Создание брони выполняется в следующем порядке:

1. Проверяются даты, пользователь, обязательность `roomId` и идемпотентность `requestId`.
2. Для автоподбора запрашиваются рекомендации и выбирается первый номер. Переданный клиентом `roomId` игнорируется. Если рекомендаций нет, возвращается 409 без создания PENDING и удалённой блокировки.
3. В первой локальной транзакции создаётся и фиксируется PENDING с фактически выбранным `roomId`.
4. Вне транзакции Booking Service вызывает confirm с `bookingId`, `requestId`, номером и датами.
5. После успешного confirm вторая локальная транзакция переводит только PENDING в CONFIRMED.
6. Клиент получает 201 и DTO со статусом CONFIRMED. Повтор того же `requestId` по-прежнему возвращает исходную бронь с кодом 200 без новых удалённых вызовов.

При бизнес-конфликте, недоступности confirm или ошибке локального подтверждения после успешного ответа Hotel Service оркестратор вызывает release с причиной `COMPENSATION`. После успешного release отдельная локальная транзакция переводит PENDING в CANCELLED, после чего клиенту возвращается исходная ошибка.

Если release или локальное завершение компенсации не удалось, возвращается 503 с явным сообщением о необходимости согласования. Успешное завершение при этом не маскирует рассогласование, а локальная бронь остаётся PENDING.

### 9.6. Реализована отмена CONFIRMED через release

Сценарий `DELETE /booking/{id}` теперь различает состояния:

- CANCELLED — идемпотентный ответ 204 без изменений;
- PENDING — локальная отмена в CANCELLED;
- CONFIRMED — сначала release с причиной `USER_CANCELLATION`, затем локальный переход в CANCELLED.

При ошибке удалённого release локальная бронь сохраняет CONFIRMED, а клиент получает ошибку. Локальная отмена после успешного release также не маскируется: сбой завершения локального обновления преобразуется в 503.

Проверка владения сохранена: пользователь не может получить или отменить чужую бронь и получает 404 без раскрытия её данных.

## 10. Этап 8 — обеспечить идемпотентность, повторы и конкурентную безопасность

Реализованы тайм-ауты и ограниченные повторы межсервисных вызовов, обработка параллельных одинаковых `requestId`, условные переходы локальных статусов и сериализация confirm/release по строке номера. Добавлены реальные HTTP-сценарии временных сбоев и конкурентные тесты на H2. Сквозная проверка через четыре запущенных приложения подтвердила отсутствие дубликатов и корректные отказы при пересекающихся датах.

### 10.1. Настроены тайм-ауты HTTP-клиента

В Booking Service создан `HotelClientProperties` с префиксом `hotel.client` и отдельными настройками:

- `base-url` — логический адрес `http://hotel-service` для Service Discovery;
- `connect-timeout` — 2 секунды;
- `read-timeout` — 3 секунды;
- вложенные настройки повторов `confirm` и `release`.

`HotelClientConfig` применяет эти значения к `SimpleClientHttpRequestFactory`, который используется load-balanced `RestClient`. Сохранён вызов экземпляров Hotel Service через Eureka без фиксированного хоста и порта в бизнес-логике.

Настройки валидируются при запуске: базовый адрес и длительности обязательны, а общее число попыток каждой операции должно быть не меньше одной.

### 10.2. Реализованы ограниченные повторы confirm и release

`HotelServiceClient` выполняет идемпотентные confirm и release через общий механизм ограниченных попыток, но получает для них независимые настройки:

| Операция | Общее число попыток | Начальная задержка | Максимальная задержка |
|---|---:|---:|---:|
| confirm | 3 | 100 мс | 500 мс |
| release | 4 | 100 мс | 800 мс |

Задержка увеличивается экспоненциально и ограничивается соответствующим `max-backoff`. При прерывании потока восстанавливается флаг прерывания, дальнейшие попытки прекращаются, а вызов завершается ошибкой недоступности.

Повторяются только временные сбои:

- сетевые ошибки соединения и чтения;
- connect/read timeout;
- ответы 500, 502, 503 и 504.

Ответы 400, 401, 403, 404, 409 и остальные не входящие в список временных ошибок автоматически не повторяются. Бизнес-конфликт 409 сразу преобразуется в 409 Booking Service, после чего оркестратор выполняет компенсацию. Получение рекомендаций для автоподбора не входит в механизм повторов идемпотентных confirm/release.

Release после тайм-аута или исчерпания повторов confirm по-прежнему обязателен, поскольку удалённая блокировка могла быть установлена. Сам release также повторяется со своим отдельным лимитом. Если компенсация не выполнена, Booking Service логирует критическое событие с `bookingId` и `requestId`, возвращает 503 и сохраняет PENDING для последующей сверки.

### 10.3. Устранена гонка одинаковых requestId в Booking Service

Уникальное ограничение `uk_bookings_request` сохранено как последняя линия защиты от дубликатов. Теперь `BookingService.create` также обрабатывает `DataIntegrityViolationException`, возникающее, когда параллельный запрос успел создать запись с тем же `requestId` первым.

После такого конфликта сервис в новой локальной транзакции:

1. Повторно читает уже зафиксированную исходную бронь вне откаченной транзакции создания.
2. Проверяет пользователя и бизнес-параметры по прежним правилам идемпотентности.
3. Возвращает исходную бронь с признаком повтора, если параметры совпадают.
4. Возвращает 409, если тот же `requestId` использован другим пользователем или с другими параметрами.

Повторный удалённый confirm для проигравшего гонку запроса не выполняется. При автоподборе по-прежнему игнорируется переданный `roomId` при сравнении идемпотентного повтора.

### 10.4. Переходы Booking выполняются условно

В `BookingRepository` добавлены изменяющие JPQL-запросы `updateStatus` и `updateOwnedStatus`. Они обновляют запись только при совпадении идентификатора, ожидаемого исходного статуса и, для пользовательской отмены, владельца.

`BookingPersistenceService` использует следующие разрешённые переходы:

- `PENDING -> CONFIRMED` после удалённого confirm;
- `PENDING -> CANCELLED` после компенсации или локальной отмены PENDING;
- `CONFIRMED -> CANCELLED` только после удалённого release.

После условного обновления сервис читает текущее состояние и различает идемпотентный повтор от конфликта. Повторное подтверждение уже CONFIRMED возвращает текущую бронь, повторная компенсация уже CANCELLED завершается без изменений. Попытка подтвердить CANCELLED или компенсировать CONFIRMED приводит к бизнес-конфликту.

Таким образом гонка ответов не может вернуть терминальный статус обратно в PENDING или незаконно заменить CONFIRMED на CANCELLED. Время `updatedAt` изменяется только фактически разрешённым условным UPDATE.

### 10.5. Усилена конкурентная защита Hotel Service

`RoomReservationService` сохраняет уникальные ограничения по `bookingId` и `requestId`, а также `PESSIMISTIC_WRITE`-блокировку строки `Room`.

Confirm теперь проверяет существующую операцию дважды:

- предварительная проверка позволяет быстро вернуть идемпотентный результат;
- после получения блокировки номера выполняется повторная проверка, поскольку параллельный confirm мог завершиться, пока текущий запрос ожидал блокировку.

Только если операция отсутствует и после второй проверки, сервис проверяет доступность и пересечения, создаёт один слот и один раз увеличивает `timesBooked`.

Release также запрашивает блокировку строки номера перед поиском и изменением записи занятости. Это сериализует release относительно confirm и других release того же номера: компенсация уменьшает счётчик не более одного раза, а повторный confirm возвращает сохранённое состояние RELEASED без воскрешения операции.

Прежний контракт идемпотентного release отсутствующей блокировки сохранён: возвращается RELEASED без создания новой записи занятости. Соответствующий security-тест сначала выявил регрессию при добавлении блокировки, после чего поведение было восстановлено и полный набор тестов повторно выполнен.

### 10.6. Добавлены конкурентные тесты на реальных транзакциях H2

Создан `RoomReservationConcurrencyIntegrationTest` с четырьмя проверками и синхронизацией потоков через `CyclicBarrier`:

- восемь параллельных confirm одного номера на пересекающиеся даты дают ровно одну активную блокировку, один `timesBooked` и семь бизнес-конфликтов;

Создан `BookingConcurrencyIntegrationTest` с тремя проверками:

Тесты используют полный Spring-контекст, реальные репозитории и транзакции H2, а не только Mockito. В Booking Service удалённый клиент заменяется заглушкой только для изоляции конкурентной локальной логики.

### 10.7. Добавлены реальные HTTP-тесты сбоев и повторов

Создан `BookingHttpFailureIntegrationTest` с локальным HTTP-сервером JDK в качестве заглушки Hotel Service. Дополнительные зависимости WireMock или другие библиотеки не добавлялись.
