# План реализации системы бронирования отелей

> **Примечание:** для каждого класса и каждого метода необходимо писать JavaDoc на русском языке.

## 1. Текущее состояние и целевая структура

Сейчас в репозитории находятся только корневой `pom.xml` и описание задания; исходного кода и тестов нет. Проект будет построен как многомодульный Maven-проект:

```text
SpringFrameWorkHomeWork/
├── pom.xml                     # parent, общие версии и зависимости
├── eureka-server/              # Service Registry, порт 8761
├── api-gateway/                # Spring Cloud Gateway, порт 8080
├── hotel-service/              # отели, номера, доступность, порт 8081
└── booking-service/            # пользователи, JWT, бронирования, порт 8082
```

Базовые технологии: Java 17, Spring Boot 3.5.x, совместимый Spring Cloud BOM, Spring Data JPA, H2, Spring Security OAuth2 Resource Server, Spring Cloud Eureka и Gateway, Lombok, MapStruct, JUnit и MockMvc. Точные версии Spring Cloud и springdoc выбрать по официальным матрицам совместимости и зафиксировать только в родительском POM.

В каждом бизнес-сервисе использовать слои `controller`, `service`, `repository`, `entity`, `dto`, `mapper`, `config` и `exception`. Наружу возвращать только DTO, не JPA-сущности. Каждый сервис остаётся самостоятельным Spring Boot-приложением со своей H2-базой; общей базы и общих JPA-модулей между сервисами не будет.

## 2. Предварительно зафиксировать контракты и правила

До реализации контроллеров записать в README итоговые URL, коды ответов и DTO, чтобы устранить неоднозначности примеров из задания:

- Booking Service: `/user/register`, `/user/auth`, административные `/user`, `/booking`, `/bookings`, `/booking/{id}`.
- Hotel Service: `/api/hotels`, `/api/rooms`, `/api/rooms/recommend`, `/api/rooms/{id}/confirm-availability`, `/api/rooms/{id}/release`.
- Gateway маршрутизирует все публичные пути Booking Service, а не только пример `/api/bookings/**`, а также публичные пути отелей и номеров в Hotel Service.
- Внутренние `confirm-availability` и `release` не публиковать через Gateway; Booking Service обращается к ним напрямую через Service Discovery.
- `/user/register` и `/user/auth` открыты без токена: пометка USER в примере задания не должна делать регистрацию и вход невозможными для нового пользователя.

Единые правила данных и ошибок:

- Даты бронирования: `startDate < endDate`; интервал считать `[startDate, endDate)`. Пересечение: `startDate < existingEndDate && endDate > existingStartDate`.
- `Room.available` означает только операционную доступность; занятость на даты определяется отдельными записями о слотах/бронированиях.
- Для автоподбора сортировка строго `timesBooked ASC, id ASC`; при `autoSelect=true` переданный `roomId` игнорируется.
- Использовать Bean Validation и единый формат ошибок, например Spring `ProblemDetail`: 400 для валидации, 401 для отсутствия/некорректности JWT, 403 для недостатка прав, 404 для отсутствия ресурса, 409 для конфликта дат или идемпотентности.
- Не возвращать хеш пароля, JWT-секреты или внутренние поля в API и логах.

## 3. Этап 1 — собрать минимальный запускаемый каркас

1. Преобразовать корневой POM в `packaging=pom`, добавить четыре модуля, Java 17, Spring Boot parent и Spring Cloud BOM.
2. Создать в каждом модуле главный класс и минимальные `application.yml`.
3. Настроить зависимости каждого приложения отдельно: Gateway остаётся реактивным, без Spring MVC; Eureka Server не содержит бизнес-зависимостей; Hotel и Booking получают Web, Validation, Data JPA, H2 и Eureka Client.
4. Подключить Lombok и MapStruct с корректной конфигурацией annotation processor.
5. Добавить Actuator health для проверки запуска, не открывая лишние actuator-эндпойнты.
6. Запустить `mvn clean verify` и затем все приложения. Проверить, что Eureka, Gateway, Hotel и Booking стартуют независимо и health-эндпойнты отвечают.

Результат этапа: пустые, но реально запускаемые сервисы и воспроизводимая сборка всего реактора.

3. Настроить маршруты Gateway на `lb://hotel-service` и `lb://booking-service` с сохранением исходных путей и заголовка `Authorization`.
4. Явно исключить внутренние операции с номерами из публичных маршрутов. Проверить, что прямой внутренний URL не дублируется публичным маршрутом.
5. Проверить регистрацию обоих сервисов в Eureka и прохождение простого публичного запроса через Gateway.

Результат этапа: динамическое обнаружение сервисов и рабочая маршрутизация без жёстко заданных адресов backend-сервисов.

2. Добавить DTO, MapStruct-мапперы, сервисный слой и локальные `@Transactional` границы.
3. Реализовать:

   - получение операционно доступных и свободных на запрошенные даты номеров;

Результат этапа: управление отелями/номерами и корректный расчёт доступности по датам без использования поля `available` как признака занятости.

## 6. Этап 4 — реализовать пользователей и аутентификацию в Booking Service

1. Создать `User` с полями `id`, `username`, `password`, `role`, уникальным username и ролью `USER`/`ADMIN`.
2. Хранить пароли только в виде BCrypt-хешей. Регистрация всегда создаёт USER, клиент не может сам назначить себе ADMIN.
3. Реализовать регистрацию и вход, проверку учётных данных и выпуск JWT с `sub`/userId, username, ролью, issuer, временами выдачи и истечения. Срок действия пользовательского токена — ровно один час.
4. Реализовать административные POST/PATCH/DELETE `/user` и проверку уникальности username. Для удаления пользователя с существующей историей заранее выбрать и задокументировать безопасное поведение без нарушения целостности БД.
5. Предусмотреть создание начального ADMIN через конфигурацию/переменные окружения, без захардкоженного боевого пароля.
6. Добавить MockMvc-тесты регистрации, входа, неверного пароля, дубликата username и административных операций.

Результат этапа: пользователи могут зарегистрироваться и получить JWT, администратор может управлять пользователями.

## 7. Этап 5 — настроить безопасность всех сервисов

1. Подключить JWT Resource Server в Hotel и Booking. Каждый сервис самостоятельно проверяет подпись, срок действия и issuer; Gateway только маршрутизирует и прокидывает `Authorization`.
2. Вынести JWT-секрет и issuer в конфигурацию/переменные окружения. Для HS256 использовать ключ достаточной длины; тестовые и локальные секреты не считать боевыми и не коммитить реальные значения.
3. Настроить Stateless Session Management, отключить ненужную для JWT CSRF-защиту и определить правила:
   - register/auth — `permitAll`;
   - личные бронирования и просмотр отелей/номеров — USER;
   - CRUD отелей, номеров и пользователей — ADMIN;
   - внутренние confirm/release — только отдельная роль INTERNAL.
4. Для межсервисных вызовов выпускать короткоживущий служебный JWT с ролью INTERNAL, не путать его с пользовательским токеном. Hotel Service должен проверять его так же, как пользовательский JWT.
5. Проверять владение бронированием на уровне Booking Service: USER может получить или отменить только свою запись, чужой идентификатор не должен раскрывать данные.
6. Добавить тесты: отсутствующий, просроченный, подделанный токен; USER на ADMIN-эндпойнте; USER на INTERNAL-эндпойнте; доступ к чужой брони; недоступность release через Gateway.

Результат этапа: независимая проверка JWT сервисами, разграничение USER/ADMIN/INTERNAL и отсутствие горизонтального доступа к чужим броням.

## 8. Этап 6 — реализовать локальную модель бронирований

1. Создать `Booking` с обязательными полями задания и дополнительными `requestId`, `updatedAt` при необходимости. Статусы: `PENDING`, `CONFIRMED`, `CANCELLED`.
2. Добавить уникальное ограничение для `requestId`, чтобы повторная доставка не создавала вторую запись.
3. Реализовать получение истории текущего пользователя, получение брони по id с проверкой владельца и отмену.
4. Создание брони разделить на короткие локальные транзакции; HTTP-вызов к Hotel Service не выполнять внутри открытой транзакции БД.
5. При повторе того же `requestId` и того же тела вернуть уже существующий результат. Тот же `requestId` с другими параметрами отклонить как 409.
6. Для отмены подтверждённой брони предусмотреть снятие занятости в Hotel Service и только затем корректный локальный переход состояния; ошибку снятия не маскировать успешной отменой.

Результат этапа: работа с личной историей и базовыми состояниями брони, готовая к добавлению распределённого сценария.

## 9. Этап 7 — реализовать двухшаговое подтверждение и компенсацию

Основной сценарий POST `/booking`:

1. Проверить даты, пользователя, `roomId`/`autoSelect` и идемпотентность `requestId`.
2. При автоподборе запросить у Hotel Service свободные рекомендации на даты и выбрать первую по правилу `timesBooked ASC, id ASC`. Если свободных номеров нет, вернуть 409 без удалённой блокировки.
3. В первой локальной транзакции создать и зафиксировать `PENDING`.
4. Вызвать Hotel `confirm-availability` с `bookingId`, `requestId`, `roomId`, `startDate`, `endDate`.
5. В Hotel Service в одной локальной транзакции заблокировать строку номера, проверить `available` и пересечения активных слотов, создать блокировку и один раз увеличить `timesBooked` согласно зафиксированному правилу статистики.
6. После успешного ответа во второй локальной транзакции Booking Service перевести только `PENDING -> CONFIRMED`.
7. При ошибке, конфликте, исчерпании повторов или тайм-ауте вызвать `release` с тем же `bookingId`/`requestId`, затем перевести `PENDING -> CANCELLED`. Release вызывать также после тайм-аута с неизвестным результатом, потому что удалённая блокировка могла уже быть установлена.
8. Если локальное подтверждение после успешного ответа Hotel не удалось, выполнить ту же компенсацию и зафиксировать ошибку.
9. Не возвращать CONFIRMED до завершения удалённого подтверждения и локального обновления. При конфликте конкретного выбранного номера вернуть 409 либо выполнить заранее ограниченный подбор следующего кандидата; не допускать бесконечного цикла.

Результат этапа: обе базы остаются согласованными без глобальной распределённой транзакции, а сбой не оставляет вечную PENDING-бронь или случайную блокировку без компенсации.

## 10. Этап 8 — обеспечить идемпотентность, повторы и конкурентную безопасность

1. В Hotel Service хранить результат операции confirm/release по `bookingId`/`requestId` и поставить уникальные ограничения. Повтор confirm возвращает результат той же операции, не создаёт второй слот и не увеличивает счётчик повторно.
2. Повтор release безопасен: уже снятая или отсутствующая после успешной компенсации блокировка не приводит к некорректному состоянию. Повторный confirm не должен воскрешать освобождённую операцию.
3. Настроить HTTP-клиент с Service Discovery, отдельными connect/read timeout и ограниченным числом повторов с экспоненциальной задержкой. Повторять только идемпотентные операции и подходящие временные ошибки; не повторять бессмысленно бизнес-конфликт 409 или ошибку авторизации.
4. Для самого release задать отдельные ограниченные повторы. Если компенсация не выполнена, логировать это как критический результат и возвращать ошибку, не скрывая рассогласование.
5. Для одновременного бронирования одного номера использовать блокировку строки Room/соответствующую сериализацию проверки и ограничения БД. Проверка пересечения и создание слота должны быть атомарны.
6. Обновления состояния Booking выполнять условно из ожидаемого статуса, чтобы повторные ответы не меняли CONFIRMED/CANCELLED в обратную сторону.
7. Не использовать непотокобезопасные общие коллекции или изменяемые singleton-поля для состояния запроса.

Результат этапа: повторная доставка не плодит данные, а конкурентные запросы на пересекающиеся даты дают одно успешное подтверждение и корректные отказы остальным.

## 13. Этап 11 — полный набор автоматических тестов

Тесты добавлять по мере реализации этапов, а в конце закрыть сквозные и отказоустойчивые сценарии.

### Модульные и web-тесты

- Валидация дат, тел запросов и граничных значений.
- CRUD отелей, номеров и пользователей; корректные 400/404/409.
- Регистрация, вход, содержимое и срок JWT, роли и владение ресурсами.
- Фильтрация доступных номеров на непересекающиеся и пересекающиеся даты.
- Сортировка рекомендаций `timesBooked ASC, id ASC`, игнорирование `roomId` при autoSelect.
- Успешное создание PENDING и последующий CONFIRMED.
- История, получение своей брони и отмена; запрет доступа к чужой записи.

### Интеграционные тесты с HTTP-заглушкой Hotel Service

Использовать WireMock или эквивалентный HTTP-тестовый сервер, чтобы проверять реальные тайм-ауты и повторы:

- Hotel возвращает успех — бронь CONFIRMED, слот один.
- Hotel возвращает бизнес-конфликт — бронь CANCELLED, корректный ответ клиенту.
- Временная ошибка исчерпывается повторами — выполняется release и CANCELLED.
- Тайм-аут после фактической установки блокировки — release всё равно вызывается.
- Сбой после успешного confirm — выполняется компенсация.
- Повторный POST `/booking` с тем же requestId возвращает исходную бронь, не вызывает повторное создание.
- Повторные confirm/release не меняют счётчик и доступность повторно.
- Ошибка самого release видна в ответе и логах, а не маскируется успехом.

### Конкурентные тесты

- Несколько потоков подтверждают один номер на пересекающиеся даты: максимум один активный слот, остальные получают 409/отмену.
- Тот же номер на непересекающиеся даты можно бронировать.
- Параллельные одинаковые requestId создают только одну Booking.
- Повторный ответ не меняет терминальный статус.

Для конкурентных тестов использовать реальные транзакции H2 и синхронизацию потоков, а не только Mockito.

## 14. Этап 12 — финальная сквозная проверка и приёмка

1. Запустить `mvn clean verify` для всего проекта и устранить все ошибки сборки/тестов.
2. Запустить Eureka, Hotel, Booking и Gateway в правильном порядке; дождаться регистрации сервисов.
3. Выполнить сценарий только через Gateway:
   - зарегистрировать USER и получить часовой JWT;
   - создать ADMIN-пользователя при необходимости;
   - ADMIN создаёт отель и номера;
   - USER получает отели, свободные и рекомендованные номера;
   - USER создаёт бронь вручную и автоматически;
   - USER видит историю, получает и отменяет свою бронь;
   - повтор requestId не создаёт дубликат;
   - конфликт дат возвращает 409;
   - USER не может выполнять ADMIN/INTERNAL операции, чужая бронь недоступна;
   - release недоступен через Gateway.
4. Проверить логи успешного и неуспешного сценариев по bookingId/requestId.
